# Soroban Escrow Contract — Security Review

Scope: `contracts/escrow/src/lib.rs` (Soroban SDK 30), its test suite, and the backend
integration in `backend/app/routers/agreements_chain.py`. Review date: 2026-11-24.
Method: source inspection, `cargo test`, `cargo llvm-cov`, and read-only Testnet queries.
No contract logic was modified by this review.

## Verified controls

| Control | Evidence |
|---|---|
| One agreement per contract instance; `init` is single-use | `lib.rs:124-126`, `lib.rs:163`; test `init_twice_fails` |
| Milestone amounts must sum **exactly** to `total_amount`; each amount positive; no empty milestones | `lib.rs:127-148`; tests `init_rejects_milestone_sum_mismatch`, `init_rejects_none_asset` |
| Asset must be an explicit Stellar Asset Contract address — no invented issuer or native-XLM shortcut | `lib.rs:66-68,133-136,217`; test `init_rejects_none_asset` |
| Only the payer can fund; only the configured `authorized` party can approve/release | `lib.rs:198-202,241-245,274-278`; tests `fund_rejects_non_payer`, `approve_milestone_by_unauthorized_party_fails`, `release_by_unauthorized_party_fails` |

| Storage TTLs extended for instance/persistent state | `lib.rs:22-28,390-402` |
| Read-only getters fail closed with explicit contract errors | `lib.rs:372-387`; `NotInitialized`/`InvalidMilestone` covered by tests |

## Residual risks and limitations

| Risk | Assessment / mitigation |
|---|---|
| One contract instance holds one agreement | Documented. Backend uses one configured contract id; production needs one instance per agreement. No functionality is invented to work around this. |
| `authorized` party can both approve and release | Separation of duties is **not** enforced on-chain. The backend restricts prepare/approve/release to the `finance_manager` role and independently verifies events; the contract trusts the address supplied at `init`. |
| No on-chain state readback in backend settlement | Events are verified independently, but `get_agreement`/`get_balance` are not invoked by the backend. Tracked as F-04: a stronger readback check is still open. |
| Duplicate `approve_milestone` returns `Ok` without an event | Idempotent by design; backend treats a missing `approved` event as `UNVERIFIED_EVENT`, so it cannot settle on a duplicate call. |
| TTL expiry of persistent milestone state | Extended by 60 days on write (`lib.rs:396-402`); a long-dormant agreement could require state restoration before use. |
| Client-supplied contract id | Now rejected by backend unless it matches the server-resolved contract (`agreements_chain.py` `_escrow_context`), closing the forgeable-settlement path found in this review. |

## Conclusion

The escrow state machine, authorization, arithmetic and refund rules are sound and heavily
tested. The material risks found during integration were in the **backend binding** of
on-chain evidence (unbound funding, cross-agreement events, client-controlled contract id,
unvalidated signed XDR), all of which were repaired in this cycle. No fabricated
transactions, hashes or balances were used as evidence.
